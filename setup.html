Point it at your project.

Two values, then a set of checks that run from this browser against the real project — the same requests the site makes, with the same key, under the same policies.

First, create the tables

In your Supabase dashboard: SQL Editor → New query. Paste the entire contents of supabase/schema.sql from this repository, and press Run. It makes two tables, the attachment bucket, and the policies that let anyone read and append while nobody may edit or delete.

You should see Success. No rows returned. Running it twice is harmless.

Then paste the two values

Dashboard → Project Settings → API. You need the Project URL and the key labelled anon public.

That key is meant to be public — it goes into a file anyone can read, and the policies decide what it may do. The one below it, service_role, bypasses every policy and must never be published. This page refuses it if you paste it by mistake.

    Put these two lines into config.js, replacing the placeholders, and commit. Nothing is kept by this page — it has nowhere to keep it.

    
  

    


    
  
    If a check fails
    
  
    Each failing row says what is wrong and what fixes it. Nearly always the answer is that supabase/schema.sql has not been run yet, or has been run against a different project than the URL above.
    
  
    None of this touches the encryption. A misconfigured project means the board cannot store or fetch anything; it never means a post goes out readable. Sealing happens before the store is ever called.
