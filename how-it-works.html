What is hidden, what is not, and what this cannot do.

A dead letter is mail nobody can deliver and nobody may open. That is the whole idea here: the board is public, the posts are not, and the site itself has no way in.

The short version

Each thread has a code. In your browser the code becomes an AES-256 key, and every post is sealed with it before it is sent anywhere. The server stores sealed bytes and the times they arrived. It cannot read a post. Nor can this site — there is nothing to read without a code, and no code is ever transmitted, logged or stored.

If you lose the code, the thread is gone. Not recoverable by us, because there is no “us” in the loop — only bytes nobody holds the key to.

What is encrypted

  • The body of every post.
  • Every attached file, sealed separately and stored apart from the post that refers to it.

What is not

  • The thread title. The rail has to list something, and that something is public. Do not put the secret in the title.
  • The shape of the conversation. How many posts a thread holds, roughly how long each is, and when each arrived. Anyone can watch a thread grow without reading a word of it.
  • The fact that a thread exists at all. If that is itself the thing you need hidden, this is the wrong tool.

The envelope

Each post is sealed with AES-256-GCM under a fresh 96-bit initialisation vector. GCM is authenticated: a post that has been altered by so much as one bit fails its tag and refuses to open, rather than decrypting into something subtly wrong.

The thread's identifier is bound in as additional authenticated data. That means a ciphertext lifted out of one thread and pasted into another will not open there — even if both threads happen to share a code. A post belongs to the conversation it was written in.

The time shown against a post comes from inside the sealed body, written by whoever posted it. The database records its own timestamp too, but that one belongs to the server and a dishonest server could put anything there. The authenticated one cannot be altered without breaking the tag.

What the binding does not do is fix the order of a thread. A server that wished to could withhold posts, show them in a different sequence, or repeat one. Each post proves it was written under the thread's key and has not been edited; nothing proves that what you are shown is all of it.

The code, and why the generated one matters

A generated code carries 256 random bits from the operating system's generator and is used as the key directly, because there is nothing left to strengthen. A code you invent yourself is stretched with PBKDF2-HMAC-SHA-256 at 600,000 iterations against a random per-thread salt.

That stretching makes each guess expensive. It does not make a guessable code safe. Everything stored here is public, so an attacker can take a copy of the ciphertext away and grind against it privately, for as long as they like, with as much hardware as they care to buy — and nobody would ever know they were trying. A memorable phrase does not survive that. The generated key does.

Telling a wrong code from a broken thread

Each thread carries a small verifier: a fixed, publicly known string sealed with the thread key when the thread was made. Entering a code opens the verifier first, so the site can say plainly that a code is wrong instead of showing a wall of nonsense and leaving you to guess why.

The verifier gives an attacker nothing they did not already have. Every post is a known-format ciphertext under the same key, so there was always something to test a guess against. Its only job is honesty about failure.

Whether a quantum computer breaks this

The honest answer is that the design is already resistant, and the reason is structural rather than clever: there is no public-key cryptography anywhere in it. Shor's algorithm — the one that breaks things outright — dismantles RSA, Diffie-Hellman and elliptic curves. Deadletter uses none of them. No key exchange, no signatures, no certificates of its own. A thread key is either 256 random bits or a passphrase stretched into 256 bits, and it is shared the way a password has always been shared: by you, out of band, to whoever you decide.

What a quantum attacker does get is Grover's algorithm, which searches a keyspace in roughly the square root of the time. Against AES-256 that turns a 256-bit search into a 128-bit one, and against SHA-256 the same. A 128-bit search is not a weakness; it is the level most of the internet considers strong today, and Grover parallelises so poorly that the practical margin is wider still. The generated code is 256 bits precisely so that halving the exponent still leaves it out of reach.

Two caveats, because the claim is only worth anything with them attached:

  • A passphrase you invented is the weak link, quantum or not. Grover does not need to search 2128 keys if the code was a phrase someone can guess in a few billion tries. Stretching raises the price per guess; it does not change the size of the field. This is the argument for the generated key and it has nothing to do with quantum computing.
  • Harvest now, decrypt later is real, and it is why this matters at all. Everything here is public, so anyone can take a copy of the ciphertext today and wait. That is the exact threat post-quantum work exists to answer, and a 256-bit symmetric key is the answer: the copy taken today is no more readable in thirty years than it is now.

The connection to the server is ordinary TLS, whose key exchange is not yet post-quantum on most browsers. That protects the metadata in transit — which rows you fetched, and when. It has nothing to do with the contents, which were sealed before the connection was opened and stay sealed after it closes.

Nothing is written to your machine

No localStorage. No sessionStorage. No cookies. No IndexedDB. No cache and no service worker. Not the code, not the key, not the decrypted text, not a thread you were reading. Closing the tab is all it takes; there is nothing to clear afterwards because nothing was put anywhere.

This costs something and the cost is deliberate. Every visit starts sealed, every thread has to be unlocked again, and nothing is remembered between sessions. The alternative is a key or a cached message sitting on a disk that outlives the person who typed it — on a shared machine, a borrowed laptop, or a device that ends up in someone else's hands.

It is checked rather than asserted. Every browser storage API is instrumented before the page's own scripts run, the board is then used properly — threads made, posts written, an image attached, a thread unlocked — and every store is inspected afterwards along with the browser profile itself. A single write would fail that test.

Where the bytes live

Rows sit in a Postgres database and attachments in an object store. The keys used to reach them are public and deliberately so — they identify the project, and what they are permitted to do is fixed by policies on the database itself: anyone may read, anyone may append, nobody may edit or delete anything, including whoever wrote it.

That last part is a real trade. It means a post cannot be taken back, and a thread cannot be tidied up. It also means no passer-by can erase someone else's work, which on a public board with no accounts is the more important of the two.

What this does not protect you from

  • Anyone who has the code. There are no accounts and no owners. The code is read access and write access at once, it cannot be revoked, and it cannot be changed without starting a new thread. Give it out accordingly.
  • Your own device. Decryption happens on the machine in front of you. If that machine is compromised, so is everything you open on it.
  • Traffic analysis. Timings and sizes are visible to the server and to anyone watching the network.
  • A code that leaks later. There is no forward secrecy. Someone who learns the code next year can read everything ever posted, because the whole history is sealed under that one key.
  • Someone with the code copying the contents out. Obvious, and worth saying: encryption governs who can read, never what a reader does next.

Why the key is forgotten when you close the tab

Unlocking a thread keeps its key in a variable for that tab and puts it nowhere else. Reload and the thread is sealed again. That follows from the section above: if nothing is written to the machine, a key cannot be either.

Reading the code yourself

The whole thing is a handful of plain files with no build step, so what is served is what was written. crypto.js is the envelope, store.js is the only thing that talks to a network, and supabase/schema.sql is every permission the database grants. If a claim on this page is not borne out by those three files, the claim is wrong and I would like to know.
